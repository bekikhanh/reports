# 振り返りレポート作成スキル（日本語・クライアント向け）

## 概要

このスキルは、日本語でのプロジェクト振り返り（振り返り）文書を、クライアントへの報告用として作成するためのガイドラインである。
Bekisoft / ベトナム系開発会社が日本のクライアントに提出する場面を想定しているが、汎用的に使用できる。

---

## ドキュメント構成（標準テンプレート）

振り返りレポートは以下の章立てで構成する。プロジェクト情報に応じて章を追加・省略してよい。

```
① プロジェクト情報（表形式）
② プロジェクト概要
③ よかった点（成果・ポジティブ面）
④ 課題・反省点（表形式 + 詳細）
⑤ 次プロジェクトへの提言
　 ├── 活かせるノウハウ
　 ├── 注意すべき点
　 └── 期待される協力体制
```

---

## 各章の作成ガイドライン

### ① プロジェクト情報

Markdown表で記載する。

| 項目 | 内容 |
|------|------|
| プロジェクト名 | 正式名称（英語名も併記） |
| 実施期間 | YYYY年M月 ～ YYYY年M月 |
| クライアント | 会社名 |
| 担当者（クライアント側） | ○○様 |
| 担当者（自社側） | 氏名 |

### ② プロジェクト概要

- 3〜5文で簡潔に記載
- システム構成（フロントエンド・バックエンド・インフラ）を箇条書きで補足
- 使用技術スタックを明示する

例：
```
○○システムは、〜を実現するための〜プラットフォームである。
- **Webアプリ**: React + Next.js
- **API**: FastAPI + PostgreSQL
- **インフラ**: AWS（ECS、RDS、S3）
```

### ③ よかった点

以下の観点から整理する（該当するものを選択）：

- **技術的成果**: 新技術の導入・実装実績
- **チームワーク**: 連携・問題対応・モチベーション維持
- **プロセス改善**: 振り返り実施・改善アクションの確立
- **クライアント連携**: フィードバック対応・信頼構築

各観点は `###` の見出しで分類し、箇条書きで3〜5項目を記載する。

### ④ 課題・反省点

**必ず表形式で記載する**（概要・詳細・原因・影響・対策の5列）。

| 概要 | 詳細 | 原因 | 影響 | 対策 |
|------|------|------|------|------|
| 1〜2行のタイトル | 具体的な事象 | 根本原因（①②箇条書き） | ビジネス・技術への影響 | 再発防止策（具体的） |

**課題の分類（よくあるカテゴリ）:**
- 仕様・要件の確認不足
- インフラ・技術選定の認識齟齬
- 品質管理・テスト不足
- SEO・非機能要件の対応遅れ
- AI・ツール活用不足
- コミュニケーション・記録不足

### ⑤ 次プロジェクトへの提言

3つのサブセクションで記載する：

**活かせるノウハウ**（箇条書き、技術・プロセス両面）
**注意すべき点**（箇条書き、課題④と対応させる）
**期待される協力体制**（箇条書き、双方向の取り決め）

---

## 文体・言語ルール

| ルール | 内容 |
|--------|------|
| 敬体 | 基本は「〜です・〜ます」調 / 表の中はデス・マス不要 |
| 主語 | 自社側は「弊社・Bekisoft側」、クライアントは「○○様・貴社」 |
| 丁寧表現 | クライアントに批判的な表現は避ける。「〜が不足していた」→「〜の確認が十分でなかった」 |
| 固有名詞 | クライアント担当者は「〇〇様」敬称をつける |
| 技術用語 | 英語のままでよい（AWS CDK, FastAPI, OpenSearch 等） |
| 番号付き課題 | 「1. 仕様・要件の確認不足」のように番号をつける |

---

## よく使う表現集

### 課題を柔らかく表現する
- 「認識の齟齬が発生した」
- 「手戻りが生じた」
- 「十分に対応できなかった」
- 「確認が不十分だった」
- 「〜の習熟が不足していた」

### 対策・提言の書き出し
- 「〜を事前に実施し、リスクを早期に特定する」
- 「〜は書面で明確化し、合意を得てから実装を開始する」
- 「〜のワークショップを実施しユースケースを共有する」
- 「〜を定例で確認する体制を設ける」

### よかった点の書き出し
- 「〜により、〜が向上した」
- 「〜を実現し、〜に貢献した」
- 「〜からの積極的なフィードバックにより、〜を加速できた」

## ワークフロー

ユーザーから振り返りレポートの作成を依頼された場合、以下の順で進める：

1. **情報収集**: ユーザーが提供した情報（Markdown、メモ、会話など）からプロジェクト情報を抽出する
2. **不足情報の確認**: プロジェクト名・期間・担当者・主要課題が不明な場合のみ質問する（一度に複数質問しない）
3. **ドラフト作成**: 上記テンプレートに沿ってMarkdownで下書きを作成する
4. **出力形式の確認**: Markdown / Word(.docx) どちらで出力するか確認する
5. **最終出力**: 指定形式で出力し、`present_files` ツールで提示する（ファイル作成の場合）

## docx出力が必要な場合

Word文書（.docx）として出力する場合は、`docx` スキルを参照してdocx-jsで生成すること。
スタイル設定の推奨：
- 見出し1: `Heading 1`（章タイトル）
- 見出し2: `Heading 2`（サブセクション）
- 表: `Table Grid` スタイル
- フォント: MS Gothic / Meiryo（日本語）、Arial（英字）
- ページ余白: 上下25mm、左右30mm（A4）
