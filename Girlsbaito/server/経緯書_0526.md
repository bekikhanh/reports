# セキュリティインシデントに関する経緯報告書
## プロジェクト名：Girlsbaito | 作成日：2026年5月26日

**全体重要度：** 🔴 **CRITICAL（最重要）**  
**現在のステータス：** 対策および復旧作業実施中  
**報告者：** 株式会社〇〇（開発チーム）  

---

### I. 概要 (Executive Summary)

2026年5月21日13:49、本番サーバーのアクセスログ解析を通じて、環境設定ファイル（`.env`）およびソースコード管理ディレクトリ（`.git`）、そして個人情報を含むシステムログファイル（`laravel.log`）が外部からWeb経由で閲覧・ダウンロード可能な状態になっていたことが判明いたしました。

調査の結果、本番サーバーの `/var/tmp/` 配下に不正なELF実行ファイルおよびシェルスクリプト（マルウェア）が配置され、`www` ユーザーの `crontab` に常駐設定が追加されていたことが確認されました。
現時点でマルウェアはアクティブに動作しておらず、リソース消費や不審なネットワーク接続も確認されておりませんが、機密情報およびユーザー情報の流出が発生しているため、最優先でセキュリティ対策と復旧計画を実行いたします。

---

### II. インシデント発生の原因分析 (Root Cause Analysis)

今回のセキュリティインシデントは、サーバー移行時の設定ミス、プロジェクト構成の特殊性、およびデプロイプロセスの不備が重なり発生したものと分析しております。

#### 1. 旧サーバーのログファイル（laravel.log 7.2GB）が残存していた原因
* **移行プロセスのクリーンアップ不足:** 新サーバーへの移行時、旧環境（XSERVER）の `storage/logs/` 内に存在していた過去の巨大なログファイルを削除せず、そのまま新環境にコピー・パッケージングして配置してしまったためです。
* **リリース前のデータ監査の欠如:** 本番リリース前に、不要な一時ファイルや過去のバックアップ、不要なログファイルがサーバー上に残存していないかを検証するプロセスがありませんでした。

#### 2. セキュリティ設定が脆弱であった技術的原因
* **Webサーバー環境の移行（ApacheからNginx）に伴う設定漏れ:**
  * 旧環境（Apache）では `.htaccess` ファイルが有効に動作し、ディレクトリへの直接アクセス制限（ドットファイルやログファイルのアクセス拒否）が機能していました。
  * Nginxサーバーに移行した際、Nginxは `.htaccess` をサポートしないため、すべての制限ルールをバーチャルホストの設定ファイル（Nginx config）に手動で移植する必要がありましたが、この設定が漏れておりました。その結果、外部からドットファイルやログへのアクセスを許す結果となりました。
* **プロジェクト構成の非標準性（Anti-pattern）:**
  * 通常のLaravelプロジェクトでは、Web公開ディレクトリ（Document Root）を `/public` 配下に限定することで、ソースコード本体や環境設定ファイルを保護します。
  * しかし、当プロジェクトでは `index.php` がプロジェクトのルートディレクトリに配置されており、Webサーバー側で手動による厳密なアクセス制限を行わない限り、`.env` や `.git`、`storage/` などの内部ディレクトリがすべて外部から直接ダウンロード可能な状態になっておりました。

#### 3. プロセスおよび組織的人的要因
* **標準デプロイチェックリストの欠如:** NginxでLaravelを構築する際、必須となるセキュリティ設定（隠しファイルの拒否設定、Document Rootの設定等）を網羅したチェックリストが存在しておらず、属人的な作業になっておりました。
* **スキルおよび経験の不足:** サーバー構築担当者が、非標準のLaravelディレクトリ構成におけるNginx設定の注意点を十分認識しておらず、リリース後のアクセス遮断の動作確認プロセスも不足していました。

### III. 各事象の詳細とリスク分析 (Detailed Incidents & Risks)

#### 1. 環境設定ファイル（`.env`）および `.git` ディレクトリの流出
* **影響範囲:** 
  * 暗号化キー (`APP_KEY`)
  * データベース接続情報 (`DB_USERNAME` / `DB_PASSWORD`)
  * Google OAuth連携キー (`GOOGLE_CLIENT_SECRET` / Google Refresh Token)
  * ソースコード全体およびコミット履歴
* **リスクと影響:**
  * `APP_KEY` の流出により、セッションやクッキーデータの改ざん、ユーザー偽装が可能になります。
  * DB認証情報の流出により、データベースへの直接接続、データの盗難、改ざん、またはランサムウェアによる暗号化のリスクが生じます。
  * Google Refresh Token の流出により、プロジェクトに関連付けられたGoogle APIサービスを無制限に不正利用され、高額請求やアカウント停止が発生するリスクがあります。
* **対策:** 
  * `APP_KEY` の再生成。
  * Google連携認証情報の即時失効および再発行。
  * Nginx構成の修正によるドットファイルアクセスの拒否（`location ~ /\. { deny all; return 404; }`）。
  * `.env` を `.gitignore` に追加し、過去のコミット履歴から環境ファイルを完全に削除します。

#### 2. `laravel.log` 経由の個人情報の流出（34名）
* **影響範囲:**
  * 7.2GBのシステムログファイルのうち、**474MB (約6.6%)** が外部IP（`212.86.126.157`）により2026年4月5日にダウンロードされました。
  * SQLのエラーログに出力されていた、ユーザーおよび管理者の個人情報 **34名分** が流出したことを確認しました。
    * 一般会員 (role=1): 5名
    * 店舗管理者 (role=2): 28名
    * 運営管理者 (role=4): 1名
    * テストアカウント: 1名
  * 流出項目: 氏名、メールアドレス、ハッシュ化されたパスワード（bcrypt）、一部の電話番号、アカウントステータス。
* **リスクと影響:**
  * bcryptハッシュ自体は強固ですが、脆弱なパスワードを使用しているユーザーの場合、オフラインの辞書攻撃により平文パスワードが解析されるリスクがあります。
  * 流出した情報（メールアドレス、電話番号）を悪用した、管理者に対する巧妙なフィッシング攻撃のリスクが高まります。
* **対策:**
  * `laravel.log` ファイルをWeb公開領域外へ即時退避または削除します。
  * 流出が確認された34名のアカウントパスワードを強制リセットし、個別に謝罪とパスワード再設定を促す通知を送付します。

#### 3. マルウェア（常駐コード）の検知
* **影響範囲:** 
  * `/var/tmp/8fbb119f/` 等のディレクトリ配下に、不正なELF 64-bit実行ファイルおよびシェルスクリプトが設置されていました。
  * システムの `crontab` に、1分毎、毎日、および再起動時にこれらのマルウェアを実行する設定が不正に追加されていました（2026年1月27日に初回設置を確認）。
* **リスクと影響:**
  * サーバー全体のroot権限が奪取された可能性があり、他システムへの攻撃踏み台化、暗号資産マイニングプロセス（Cryptojacking）への悪用、あるいはバックドア設置による長期的な機密情報窃取のリスクがあります。
* **原因の推測:**
  * 攻撃者は流出した `.env` 内の認証情報を利用、あるいはWebアプリケーションの脆弱性を利用してサーバー内に不正に侵入し、一般Web権限（`www`）でマルウェアをアップロードして永続化を図ったと考えられます。
* **対策:**
  * 不正ファイルの安全な隔離および完全削除。
  * 不正な `crontab` タスクの完全消去。
  * 悪意あるプロセスがアクティブだった6週間（1/27～3/12）にどのようなコマンドが実行されたか、サーバー詳細ログのフォレンジック調査を実施します。

### IV. 対応プランと今後のスケジュール (Response Plan & Timeline)

#### Giai đoạn 1: 緊急対応（即時～本日中）
* **1.1 悪意あるIPの遮断:** スキャナーBot IP（`94.26.88.32`）からの接続をファイアウォール（Security Group）にて完全遮断します。
* **1.2 SSHセキュリティの強化:** `/root/.ssh/authorized_keys` から不要・不明な公開キーを全て削除し、SSH設定で `PermitRootLogin no` を適用・再起動します。
* **1.3 マルウェアの駆除:** `/var/tmp/` 配下の不正 tệp 削除、および不審な `crontab` 設定を全消去します。
* **1.4 Webサーバーの保護:** Nginxにてドットファイル（隠しファイル）および不要な設定ファイルへの直接アクセス制限を設定し、Nginxをリロードします。
* **1.5 アプリケーション情報の更新:** `php artisan key:generate` を実行して `APP_KEY` を再生成。Google API認証情報を失効させ、再発行・更新します。

#### Giai đoạn 2: 短期対応（夜間および2〜3日以内）
* **2.1 DB認証情報の更新:** `DB_PASSWORD` を変更し、MySQLユーザー `gbaito` の接続元ホスト設定をワイルドカード（`%`）からローカル（`localhost`）へ変更します（サービス影響を抑えるため夜間に実施）。
* **2.2 ログの完全処理:** 巨大な `laravel.log` を公開領域から完全削除し、Gitリポジトリのインデックスから `.env` とログファイルを完全に除外します。
* **2.3 ユーザーアカウントの保護:** 対象34名のパスワードを強制リセットし、個別に謝罪およびパスワード変更案内のメールを送信します。
* **2.4 詳細フォレンジックの実施:** システム監査ログに基づき、攻撃者のシステム内での詳細な操作履歴を解明します。
* **2.5 サーバー構成の再監査:** パスや権限設定、その他実行サービスについて包括的な再点検を行い、構成ミスを排除します。

#### Giai đoạn 3: 中長期対応（1ヶ月以内）
* **3.1 機密情報管理ツールの導入:** AWS Secrets Manager 等の機密情報統合ツールを導入し、`.env` ファイルへの重要情報直接記述を排除します。
* **3.2 CI/CD セキュリティスキャン:** Pipelineに Gitleaks 等の自動スキャナーを組み込み、機密情報のGit漏洩を未然に防止します。
* **3.3 ペネトレーションテスト:** 外部の専門セキュリティ機関によるシステム全体の疑似侵入テスト（セキュリティ監査）を実施します。
* **3.4 WAF（Web Application Firewall）の導入:** 不正なアクセスや脆弱性スキャンを自動的にフィルタリング・ブロックする保護シールドを構築します。
* **3.5 開発プロセスの標準化:** Laravel / Nginx 向けの安全なデプロイチェックリストを策定し、エンジニア向けにセキュリティトレーニングを実施します。

### V. 再発防止策 (Preventative Measures)

1. **最小権限の原則 (Least Privilege) の徹底:**
   * 本番サーバーへのroot直接SSH接続を無効化。作業者は個人アカウントで接続し、操作履歴を確実に監査可能にします。
   * DB等の内部接続は必要最小限のホスト・権限に限定します。
2. **安全なデフォルト構成 (Secure by Default) の順守:**
   * ドキュメントルートは必ず `/public` に設定し、フレームワークの内部設計に頼ったアクセス制御を排除します。
   * 機密ファイルはデプロイ手順書に沿って確実にGit管理対象外にし、本番専用環境に安全に注入します。
3. **リアルタイム監視および早期アラート:**
   * 本番環境におけるSSHログインやクリティカルな設定ファイルの変更を検知した際、管理者チャンネル（Slack等）へリアルタイムで通知するアラートシステムを導入します。
